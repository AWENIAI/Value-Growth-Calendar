# 2026-09 日历提醒连续失败复盘

## 结论

本次事故的根因不是单个命令失败，而是验收目标错位：

服务器执行成功、ICS 生成成功、GitHub 同步成功，不等于用户实际收到可用提醒。

## 第一性原理

用户真正需要的是：

1. 到指定时间能看到当天有效内容。
2. 如果有提醒诉求，提醒时间必须没有过期。
3. 如果数据源未更新，系统必须明确给出当天状态，而不是静默无变化。
4. 如果需要强实时推送，ICS 订阅不是可靠推送通道，必须另接 Bark / 飞书 / 企业微信 / Telegram / 邮件等主动通知通道。

## 事故表现

连续多次出现“系统内部看似成功，但用户没有收到有效提醒”。

错误的验收方式包括：

- 只检查 systemd exit code。
- 只检查 HTTP 200。
- 只检查 GitHub push 成功。
- 只检查 ICS 文件包含某条数据。
- 没有检查 DTSTART / DTEND / VALARM 是否仍在未来。
- 没有区分“订阅日历刷新”与“主动消息推送”。

## 关键错误

### 1. 把内部成功误判成用户成功

内部成功只能说明程序运行过，不能说明用户收到提醒。

以后必须用用户可感知结果作为 P0 验收标准。

### 2. 没有及时承认 ICS 的机制限制

ICS 订阅是客户端拉取，不是服务器主动推送。Apple / Google 何时刷新，服务器无法强制控制。

### 3. 没有检查提醒时间是否已经过期

阿文风险提醒日历曾出现：18:00 生成，但事件时间被写成当天 08:00，提醒时间已经过期。

### 4. 数据源未更新时静默

阿文价值成长日历曾出现：15:15 执行成功，但指数数据源仍停留在上一交易日，导致当天没有新事件。

## 以后强制验收清单

每次修改、部署或修复日历项目后，必须验证：

1. systemd timer 是否按预期触发。
2. service 日志是否成功。
3. ICS 是否生成。
4. ICS 是否包含当天事件或当天状态事件。
5. DTSTART / DTEND 是否符合提醒目标。
6. VALARM 是否不会落在过去。
7. 公网订阅 URL 是否返回最新内容。
8. GitHub HEAD 是否等于 origin/main。
9. 如果用户目标是“收到推送”，必须说明 ICS 不能保证，并提供主动通知通道。

## 防复发规则

不得再把以下结果单独称为成功：

- HTTP 200
- npm run 成功
- GitHub push 成功
- systemd active
- ICS 文件存在

只有当“用户目标对应的业务断言”通过，才能称为成功。
